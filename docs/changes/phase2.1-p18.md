## P18-01 扫描 `warnings = "-79"` —— 实际是 **3 个包**，不是 10 个

```
http/moon.pkg ｜ pg/moon.pkg ｜ redis/moon.pkg
```

而且每个包里**都写了理由**（三个包一字不差）：

> 新版 moon 把 `derive(Eq/Debug)` 的隐式提升标为弃用（error code 79）——
> 本地工具链版本较旧、看不到它，**CI 上会因此报 17 个 error**。这里收窄掉。

**所以 `-79` 不是"偷懒收窄"，是跨版本兼容措施。** 实测也印证了：

| 操作 | 结果 |
|---|---|
| 去掉其中一个包的 `-79` | `moon check` → **37 warnings** |
| 去掉全部三个 | `moon check` → **48 warnings, 0 errors** |

⚠️ 注意本机是 **0 errors** —— 因为**本机的 moonc 版本较旧、根本不报 79**。
而注释说 CI 上（新工具链）它会是 **error**。

## 于是"迁移"这件事在本机做不了（RULE-01 的直接后果）

要真正清掉它，得**改代码**（给每个 `derive` 加显式 `pub extend … { … }` 声明，约 17 处），
而这恰恰是**本机看不到那个 warning** 的那一项 —— 也就是说：

- 改完在本地**无法验证**是否修对（本地根本不报 79）；
- 唯一能验的地方是 CI，而 CI 一旦红就是**构建失败**。

**所以这批没有动它**：把 `-79` 删掉会**直接坏 CI**，而按现在的做法改代码又**验证不了**。
硬要说的话，正确路径是"先让 CI 跑一次带警告的构建、看清那 17 个 error 的位置，再逐个加声明" ——
那是一次独立改造，不该混在"清技术债"里顺手做。

（三个包的文件在实验后已**完全恢复**，`git diff` 为空。）
