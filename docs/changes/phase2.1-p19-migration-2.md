**结论：改 JS 源码只用 `edit_file` / `write_file`，不用 python 拼。**

## 收尾：那两个"长期红灯"的真相

### `verify-dash.js` 的 7 个失败 —— **测试过时**，不是实现坏了

用 `git show HEAD:` 跑原版对比，**原版同样 10 通过 / 7 失败**，失败项是：
日历 0 格、今天高亮 0、待办输入框没有、便签 textarea 没有、日程区空……

查下去发现根因很直白：

```
脚本期望的 id：dashCalendar / dashTodos / dashNoteArea / dashAgenda
实际 UI 的 id：dashClock  / dashDate / dashGrid / dashAdd      ← index.html 里就这几个
```

那四个 id 在 `dash.js` 里**出现 0 次** —— **工作台 UI 早就重写了，这个脚本没跟上**。
所以它不是"实现坏了"，是**测试在测一套不存在的 UI**。

处置：给它加了 **UI 版本检查**，检测到新 UI（`dashGrid` 在、`dashCalendar` 不在）就明确报

```
[SKIP] 工作台 UI 已重写（现在是 dashClock/dashDate/dashGrid/dashAdd）
结果：0 通过 / 0 失败 / 共 0 项（SKIP：被测 UI 已变更）
SKIP_REASON=ui-rewritten
```

**为什么不直接删掉它**：脚本本身记录了"工作台该有哪些行为"，按新 UI 重写还有用；
**为什么不是让它继续报 FAIL**：`SKIP` 与 `FAIL` 是两件事 ——
"测试没跟上实现"不该伪装成"实现坏了"，也不该让人以为它验过了（这正是 P19-24 的语义）。

### 顺带又发现一处坏兜底

`verify-dash.js` 既没有 `log` 也没有 `dump`，所以它的 `.catch` **也是坏的**
（异常时会报 `dump is not defined` 而不是给出原本的 FATAL 原因）。
前面那轮"修 30 个兜底"的批量替换**没覆盖到它**（它的写法略有不同）。
这次把剩下的写法差异也统一了（又 11 个），复查"引用了不存在符号的兜底"= **0**。

> 这条值得记：**批量替换"看起来一样"的代码时，总有几种变体会漏掉** ——
> 所以每次批量之后都要用**不同的判据**复查一遍（这次是"跑起来看"才发现漏的）。

## 最后那个 `verify-dash-v2.js`：三个**测试自身**的问题

它"跑不通"（exit=1、没有结果行），我原来以为是 UI 过时。查下来**全是脚本自己的毛病**：

### 1. 点错了按钮（这是主因）

```js
const next = document.querySelectorAll('.cal-bar button')[2]   // ← 以为 [2] 是"下个月"
```

实际 `.cal-bar` 里依次是 `[0] 上个月` `[1] 下个月` `[2] 回到今天` —— **`[2]` 点的是「回到今天」**，
所以月份**根本没翻**。于是后面一串断言全跟着错：标题还是 9 月、看不到 10 月国庆、
`2026-10-01` 的格子不存在（`no-cell`）、最后 `getBoundingClientRect` 对 null 报错。

**看着非常像"UI 过时"，其实只是点错了按钮。** 改成按 `title === '下个月'` 取之后就通了。

> 这条最能说明"为什么不能靠猜"：如果按"看起来像 UI 变了"就把它 SKIP 掉，
> 那这个脚本就**永远**验不到东西了 —— 而它其实一直在正常工作，只是点错了地方。

### 2. 截图那一步没有保护

27 项断言**全过**之后，崩在最后截图：`UnknownVizError`（`capturePage` 的偶发问题）。
`verify-theme.js` 里早就有 `safeShot` 保护并注释了原因，`dash-v2` 漏了。
补上之后截图失败不再中断（日志会写"截图失败（不影响结论）"）。

### 3. 测试污染：localStorage 累积

`chk('新建的日程写进 localStorage', stored.length === 1)` —— 但日程存的是
`{"2026-10-01": [...]}`，脚本每次跑都往**同一天追加**，于是第二次起必然失败
（我观察到数组从 3 条涨到 4 条）。测试前先 `removeItem('moonbit-dash-events')` /
`'moonbit-dash-notes'` 之后，**连跑两次都是 27/0**。

> 这条和之前"4 个长期红灯"是同一类：**测试自己没有隔离好**，却表现得像产品有问题。

## 最后一步：按新 UI 重写 `verify-dash.js`（从 10/7 变成 13/0）

它原来是 SKIP（明确标注"被测 UI 已变更"）。既然要收口，就**按新 UI 重写**。

### 先做去重

把两边的断言列出来对比，发现 `verify-dash-v2.js` 已经覆盖了：日历渲染 / 今天高亮 /
月份导航 / 翻月 / 点选日期 / 日程（新建、存 localStorage、菜单）/ 便签可编辑。

所以重写时**只保留 v2 没验的那 5 项**：

| # | 断言 | 依据 |
|---|---|---|
| ① | 时钟在走 | `#dashClock` 输出 `HH:MM:SS`，**并且两秒后确实变了**（不是静态文本） |
| ② | 日期含「星期」 | `#dashDate` 输出 `YYYY 年 M 月 D 日 · 星期X` |
| ③ | 待办区有输入框 | `#dashGrid` 里有文本输入框且带 placeholder |
| ④ | 图标各不相同 | 比较各 `<svg>` 内 `<path d>` 的**指纹**，不同指纹数 ≥ 2（防"同一个图标复制"） |
| ⑤ | 「项目」标签有编辑器 | 点 `a[data-view="project"]` → 视图可见且含编辑器容器 |

结果：**13 通过 / 0 失败**（原来 10 通过 / 7 失败）。

### 一个细节

时钟那条特意做了两次采样（隔 2.2 秒）——只断言"格式是 HH:MM:SS"的话，
**一个写死的静态字符串也能通过**。多采一次才能证明它在走。
