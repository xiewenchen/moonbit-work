## 四件套为什么缺一不可

| 字段 | 角色 |
|---|---|
| `ok` | **唯一**的成功/失败判据（别用"有没有 error 字段"反推） |
| `code` | **机器可判**的原因（`NO_CLIENT` / `NOT_RUN` / `FORBIDDEN`…），界面据此分支 |
| `error` | **人可读**的说明，直接给用户看 |
| `data` | 成功时的载荷（可为 `null`） |

> **只有 `error` 没有 `code` 时，界面只能按「文案」分支 —— 文案一改逻辑就坏。**
> 这就是这一层存在的理由。

## ★ 实测出来的起点：合规率约 **8%**

`audit-ipc` 现在会数一遍：
- 带 `ok` 的返回：**397 处**
- 其中带 `code`：**31 处** → 合规率约 **8%**
- 带 `data` 的：**2 处**

**这不好看，但它是真实的起点。** 我没有去改那 400 多处（那既违反"一次一个"，
也会在一个提交里混进几百处语义微妙的改动）。采取的是**渐进收口**：

1. 新建统一构造器 `ipc-result.js`（`ok()` / `fail()` / `fromError()` / `conforms()` / `normalize()`）；
2. `audit-ipc` 把合规率**报出来**，作为后续收口的度量；
3. 约定：**新代码用构造器**；旧代码逐步迁移。

## 三种"失败"必须能分开

`NO_CLIENT`（本机没装客户端）、`NOT_RUN`（还没跑过）与 `INTERNAL`（真出错）是**三件事**，
在界面上也该长得不一样。测试断言三者的 `code` **互不相同** ——
这与 Quality 的 `NOT_RUN ≠ FAIL`、数据库的 `NO_CLIENT ≠ 连接失败` 是同一条原则。

## `normalize()` 是给渐进迁移用的

它能把旧形状读成统一结构并**标出额外字段**（不丢信息），但**不会**自动替换旧代码。
裸值默认被判为"不是统一结构"（**宁可报出来，也不要猜它是什么**）。
