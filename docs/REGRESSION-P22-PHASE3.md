## 二、9 个失败——**逐条处理结果**

### A 类：**不是失败，是"调用方式"**（3 个）→ 按用法传参后**全部通过**

| 脚本 | 原来 | 按用法跑 |
|---|---|---|
| `verify-open-url.js` | 打印用法后退出 | `<项目目录>` → **exit 0** ✅ |
| `verify-rename.js` | 打印用法后退出 | `<项目根>` → **3/0** ✅ |
| `verify-run-e2e.js` | 打印用法后退出 | `<项目目录>` → **exit 0** ✅ |

> 它们**需要传项目目录**。批量跑时没传参，于是它们打印用法后退出 ——
> **这是调用方式的问题，不是它们坏了**。

### B 类：**环境/自身定位问题**（3 个）→ 修好 1 个、解释 2 个

| 脚本 | 原因 | 处理 |
|---|---|---|
| `verify-harness.js` | **它不是 verify 脚本，是公共库**（被其它 verify `require`） | **不该被当脚本跑**（库本身由 `test-verify-harness.js` 守） |
| `verify-widgets.js` | `capturePage` 抛 `UnknownVizError` | **已修**：截图包 try/catch → **15/0** ✅ |
| `verify-strapi-parity.js` | 同上 | **已修**截图部分；但它**另有 8 项配色断言失败**（见 C 类）|

> `UnknownVizError` 是"无 GUI / GPU 被禁"时 `capturePage` 的正常表现。
> 更关键的是：**截图失败曾让整个脚本以 FATAL 退出，掩盖了它上面那些断言其实全过**。
> 截图是**附加产物**，不该决定验证结论。

### C 类：**真问题**（3 个）→ 修好 2 个、说明 1 类

| 脚本 | 根因 | 处理 |
|---|---|---|
| `verify-project-memory.js` | P17 把 `fs:write` 收窄成"**必须已打开项目**才能写"，而它从来没调过 `openProject`（只把 ROOT 当参数传） | **已修**（先 `openProject`）→ **38/0** ✅ |
| `verify-agent-ui.js` | 轮询 45s 等 AI 回复；本机**没有可用模型通道** | **已修**：改为**显式 SKIP**（环境不满足 → SKIP，不是 FAIL）→ **exit 0** ✅ |
| `verify-strapi-parity.js` / `verify-strapi-final.js` | **"抄 Strapi UI"时代的对比脚本**：它断言 IDE 的配色**等于** Strapi 的配色 | **前提已变**：主题已 token 化（日间/夜间），颜色**本来就不同**了 → **已明确标记过时**（见下） |

> 最后这一条**不是缺陷**：那些断言问的是"我们和 Strapi 长得一样吗"，
> 而现在**长得不一样是有意的**（token 化 + 两套主题）。
> 这类"前提已变"的脚本应当**明确标记过时**，而不是继续以红灯示人 ——
> 否则它会长期淹没真正的回归。

## 三、本轮修出来的一个真实认知

**`fs:write` 的守卫比"只能写工作区内"更严** —— 它还要求**当前已打开项目**：

```
未打开项目 —— 拒绝写入（避免"没打开项目也能改磁盘上的文件"）
```

而 `verify-project-memory.js` 一直只用 `ROOT` 当**参数**、从没 `openProject` ——
于是它在 P17 之后**静默地不再验证它想验证的东西**。
这条是**全量回归**挖出来的，不是读代码能看出来的。

## 四、这份报告**没有**做的事（如实说明）

- **没有**为了让数字好看而删掉或改名任何 `verify-*.js`；
- **没有**把"前提已变"的脚本当成通过 —— 它们是**过时**，会单独标注；
- **没有**把 Electron 那 55 个塞进 CI（CI 是 Linux 无显示环境）。

> 这暴露了一个**真实缺口**：**55 个 Electron verify 平时不在任何人手里跑**。
> CI 只跑纯 Node（55 个）+ 静态门禁；Electron 那条线靠**发布前手动全量**。
> 本轮就是那次手动全量 —— 所以它才挖出上面这些。

## 六、后续处理：把"前提已变"的脚本明确标记过时（2026-09-26 同日）

P22 报告写完后就动手了 —— 因为**让两个"前提已变"的脚本继续以红灯示人，只会长期淹没真正的回归**。
照 `verify-dash.js` 的手法（那次是**重写**；这次没有"新 UI"可重写，所以改为**标记过时**）：

- 头部写清**为什么过时**（前提变了，不是缺陷）+ 替代做法（将来要重做就断言 token，而不是断言等于 Strapi）；
- 运行时**仍然跑完、仍然逐项打印**（便于人工比对）；
- 退出码按"过时"处理，**不参与回归判定**；
- **不过静默** —— 每次都会打印一行明确的"本脚本已过时：<原因>"。

| 脚本 | 结果 |
|---|---|
| `verify-strapi-parity.js` | **exit 0** ✅ 且打印过时说明 |
| `verify-strapi-final.js` | 已加标记与三层兜底（结尾 / `.catch` / `uncaughtException`），但它的失败是**渲染进程崩溃**（electron 层），退出码仍为 1 —— **会打印过时说明，但不改退出码**。如实记在这里，不假装已解决 |

> 于是"全量回归的红灯"收敛成：**`verify-harness`（是库不是脚本）+ `verify-strapi-final`（过时，electron 层退出码改不动）**。
> **产品代码的回归数为 0。**
